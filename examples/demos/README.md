# examples/demos/
Purpose: demo programs in assembly (`spec/asm_syntax.md`): Pong first, a reversible cipher, a sort that exposes
its garbage. Owner: **games**.

## Reversible idioms (starter notes)
- No `MOV/AND/OR`. Copy a value: `xor rdst, rsrc` into a zeroed `rdst`. "Clear" only by undoing how it was made.
- Update with `addi`/`add`/`sub`. Negate: `not r; addi r,1`. Conditional change: branch with `br`/`lnd` (SPEC section 6 examples).
- **Draw with XOR.** `xst` a sprite pixel to draw it, `xst` the same value again to erase it. This avoids "overwriting" the framebuffer.
- Load a big constant with `xori r, imm` (zero-extended, reaches 0x3FFFF). Framebuffer base is `0x20000`.
- Input: keep a cursor register; poll `COUNT` at `0x30001`; read event k at `0x30002+k`; `addi cursor,1` to consume. Running backwards un-consumes for free.
- Keys: each input event is `code | (released ? 0x100 : 0)`. A press is the plain code (uppercase ASCII, Space 0x20, Enter 0x0D, arrows Up/Down/Left/Right = 0x80/0x81/0x82/0x83); bit 8 means released. See `spec/input_tape.md`.
- Frames: add 1 to the word at `0xFFFF` once per frame so the debugger can step by frame (SPEC section 11.7).
- Pacing: read `TIME` at `0x30000`; busy-wait loops are fine (they are reversible and just spend steps).
- Garbage is expected. Note what each program leaves behind; the benchmarks and writeup will report it.
- Before the assembler exists: write a plain-JS model of the game and fix the register/memory layout first.

## Programs
Both demos keep their data **on the screen** (framebuffer words are pixels), so the screen is the visualisation and the
programs draw nothing. This is the trick for visuals with no boilerplate: put the data where the screen is.
- `cipher.s`: **Speck64/128** (a published add-rotate-xor cipher) encrypting a 32-character message in place on the screen.
  Row 0 first shows 8 dull grey-blue pixels (the plaintext), which turn into 8 random colours (the ciphertext). Flip the
  direction toggle and the same program decrypts. 42 instructions, 1,203 steps, no garbage (every temporary register ends at
  zero), and it reproduces the official Speck64/128 test vector on the machine. The message starts in the data region (programs
  load there) and is moved onto the screen first: `xld`, `xst`, `xst`, `xld` moves a word with nothing overwritten.
- `sort.s`: a **reversible sort of 8 numbers that exposes its garbage**. The list is row 0 of the screen (values are colours:
  small = green, large = red); the garbage is row 1: one pixel per compare-exchange, cyan = swapped. Sorting loses information, so
  the 19-step network records a bit per step; sorted list + garbage = the original, so direction -1 unsorts exactly and clears
  the garbage. 341 instructions, 311 steps; 19 garbage pixels where the theoretical minimum for 8 items is 15.3. Step through it
  and watch the compared pair vanish into registers and return swapped. Generated by `examples/demos/tools/gen_sort.mjs`, which also
  proves the network sorts all 256 0/1 inputs. Tested on 25 random inputs on both engines.
- `pong.s`: **reversible Pong**, drawn on the screen. W / S or Up / Down move the cyan paddle (left edge, hold to keep moving); the
  white ball bounces off all four walls; each return to the left edge with the paddle there is a hit and **lights a yellow 2 x 2 score
  block** on the right half (one block per hit, so the row of yellow blocks is your score); otherwise the program halts: **game
  over, and stepping back resumes the game**. 275 instructions, 238 lines of plain source (no generator), about 400 steps per frame.
  It uses `.with`, `.compute`/`.uncompute`, `.plot` and procedures, which is what made it small. How it stays reversible:
  - The ball has **no bounce logic**: each axis keeps an unfolded position that just counts (a phase that wraps by itself) and the screen
    position is its triangle-wave fold, so a bounce is the fold turning round: no decision, nothing lost, no garbage. The fold is a
    procedure that XORs its result in, so calling it twice clears what the first call set (clear with the old phase, move, set).
  - Drawing is XOR (the same instruction draws and erases); every temporary is zero at the end of each frame.
  - **Input is the one thing that must be recorded**: each frame the latest key event and the event count are filed in a log (data memory
    from 0x1000, 2 words a frame). That log is the program's only garbage: 8 bytes a frame (and zero while nobody presses a key) against
    about 19 KB a frame of diary history on the logging engine.
  - Simplification: the paddle wraps around the top and bottom instead of stopping at the edge (stopping it would need a recorded bit per
    blocked move). Game over is a one-sided halt, which needs no assertion bookkeeping (`.fi al`).
  - Use **Back / Run back / the scrubber** to rewind Pong, not the Direction toggle: a program that reads the input window is not exactly
    self-inverse under direction -1, because the window follows machine time (spec/input_tape.md). Time travel is always exact.
  - Tested on both engines against an independent model of the game after every frame (screen, registers, log, and "every temporary is
    zero"), including a 400-frame game that steers the paddle to six returns, game over at frame 53 with no input, rewind and scrubbing.
- Idioms they demonstrate: moving words between memory and registers without overwriting; nested `.loop` macros; `.if` with a flag
  register for the `.fi` assertion (the `.if` test registers may change; only the `.fi` assertion registers matter); constants and
  temporaries with `.with` and `.compute`/`.uncompute`; XOR drawing with `.plot`; self-inverse procedures.
- Watch (and play) them: `cd web/wasm && npm run playground` (see `web/wasm/README.md`), including the **Compare engines** view.
- To run any program headless: `node asm/dist/cli.js examples/demos/x.s -o x.rvm`, then `build/default/rvm_run x.rvm --engine reversible --rewind`.

## pong.rev
`pong.rev` is the same game as `pong.s` written in the `rev` language (`lang/`), compiled with `npm run rvmc -- examples/demos/pong.rev -o pong.rvm`. It draws the identical court frame for frame (tested against `pong.s`), and adds a permanent wall and a score shown as a number, which `pong.s` does not have (it lights yellow blocks). Measured before those additions it cost about 22 percent more steps per frame than the assembly; see `lang/README.md`. Read it next to `pong.s` to see what the language buys: the reversible tricks (unfolded phases, XOR drawing, self-inverse procedures, recording input) stay, the register juggling goes.
