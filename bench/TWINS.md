# Fair baselines: conventional twins vs the reversible programs

Generated by `npm run report` in `bench/twins` (about 20 seconds). Definitions: `spec/SPEC.md` section 12. Every
number below is measured, not estimated; the tests in `bench/twins/test` check that each twin draws the same picture as
the reversible program on the real engines, and that the tight diary and the checkpoints rewind **exactly**.

## What is being compared
- **Reversible**: `examples/demos/sort.s` and `examples/demos/pong.s` on the reversible engine. No history in the machine; the program
  keeps its own garbage.
- **Conventional twin**: the same job written for an ordinary overwriting machine (`bench/twins/src/twins.ts`, run by a
  small conventional machine in `src/conv.ts` with the same memory map and input window). Same network, same game, same
  pixels. Nothing is stored for undo by the program itself.
- **Naive diary**: our logging VM on the *reversible* program (48 bytes a step; measured).
- **Tight diary**: a real bit-packed history for the *conventional* twin: per overwriting step the old value's significant
  bits plus a 6-bit length, per join the index of the predecessor. It rewinds exactly (tested). This is the strongest
  simple diary we know how to write; a cleverer compressing one could be smaller.
- **Full-width diary**: 32 bits per overwriting step, the worst-case count `bits_erased` of SPEC 12.2.
- **Checkpoint and replay**: a snapshot every K steps (registers plus every word the program ever writes); to go back,
  restore the nearest earlier snapshot and run forward.

Step overhead of reversibility on this program: **3.0x** instructions, **3.0x** code.
The information floor for sorting 8 distinct numbers is log2(8!) = 15.3 bits; the reversible sort keeps at most 19 bits
(one per comparator, 14 set this time), so it sits within a few bits of the floor. The tight diary keeps
2,152 bits, because it logs overwritten *values*, not the one bit of *why*.

### Memory against the time to go back (Pong, whole run)

"Undo steps" is how many instructions it takes to move back to an earlier moment, in each machine's own steps.
Going back one frame costs 399 inverse steps on the reversible machine and 123 undo steps on the diary.

| strategy | memory held after the run | to go back 1 step | to seek to an arbitrary earlier time (mean / worst) |
|---|---|---|---|
| naive diary (reversible program) | 3,828,912 B | 1 undo step | 39,885 / 79,769 undo steps |
| tight diary (conventional twin) | 25,152 B | 1 undo step | 12,252 / 24,503 undo steps |
| checkpoint every 100 steps | 245,016 B (246 snapshots x 996 B) | up to 99 steps of replay | 50 / 99 steps of replay |
| checkpoint every 1,000 steps | 24,900 B (25 snapshots x 996 B) | up to 999 steps of replay | 491 / 991 steps of replay |
| checkpoint every 10,000 steps | 2,988 B (3 snapshots x 996 B) | up to 9,999 steps of replay | 4,501 / 9,984 steps of replay |
| **reversible** | **1,600 B** (its log; 0 B in the machine) | 1 inverse step | 39,885 / 79,769 inverse steps |

How the memory grows with the length of the run (bytes per frame, from this run):
naive diary 19144.6, tight diary 125.8, checkpoints every 10,000 steps 14.9,
reversible 8.0 (its input log; the conventional rows also need an input tape of 4.2 B/frame here).

What this table says:
- Against both diaries the reversible program wins on memory by a wide margin, and the machine itself needs no history.
- **Checkpoint-and-replay is a serious competitor, not a straw man.** With a snapshot every 10,000 steps it holds about as
  much as the reversible program log does, and it seeks to a far-away time in at most K steps, where reversible and diary
  both walk one step per step. Pong has a tiny writable state (a few hundred words); a program with a large state pays that
  per snapshot, while the reversible machine does not. We did not measure such a program.
- What reversible does that checkpointing does not: stepping back *one* instruction costs one inverse step (a checkpoint
  scheme replays up to K-1), and nothing is lost between snapshots. It pays for that with the extra instructions above.

## Reading this honestly
- The reversible engine holds **no history**, the program keeps only its input log (Pong) or at most 19 bits (sort), and in
  exchange it runs **3.3x (Pong) and 3.0x (sort)** more instructions than the twin. That overhead is the price, and it is real.
- Against the **naive** diary the saving is enormous. Against the **tight** diary it is large but not astronomical: Pong
  needs 25,152 B over 200 frames. Against checkpointing the memory is comparable on this program. Quote the tight diary and
  the checkpoint rows as the headline comparison, not the naive one.
- The tight diary is the best simple design we know. Compressing diaries (delta coding, entropy coding) could shrink it further;
  we did not build one. Treat "tight" as a strong baseline, not a proven floor.
- Instruction counts are for our two toy machines. Wall-clock speed is in `bench/RESULTS.md` (the reversible engine rewinds 2 to 5 times
  slower per step than the logging engine).
- The twins draw with XOR so the pictures match pixel for pixel, which a conventional programmer would not need to do; plain stores
  would be slightly shorter. The conventional machine has no call/return, so helper code is inlined.
- One game, one sort, one input pattern. Do not extrapolate.
